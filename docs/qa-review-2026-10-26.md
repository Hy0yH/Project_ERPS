## 3. 핵심 결함의 구체적인 개선 방향

### QA-005. 집계 실패와 서로 다른 갱신 시점

읽기 전용으로 확인한 미스릴 이상·14일 스냅샷의 저장 시각은 다음과 같다. 날짜와 시각은 모두 KST다.

- 실험체: **2026-10-26 21:10:39**.
- 조합: **2026-10-20 22:57:26**.
- 10/26 21:05:22 수집 실행에서는 경기 187건 저장에 성공했다. 이어진 스냅샷 요청은 21:08:46 실패했고 재시도도 21:12:23 실패했다.
- 수집 서버 오류 로그에는 PostgreSQL 57014, statement timeout이 반복되어 있다.

현재 buildSnapshots는 실험체·조합·비교 벤치마크를 순서대로 저장하고, 조합 전체를 한 번의 upsert로 보낸다. 독자는 테이블마다 최신 결과를 따로 선택한다. 실패 지점에 따라 일부 테이블만 새 결과가 될 수 있는 구조다. **실패한 SQL 문 자체는 추적하지 않았으므로 대량 조합 upsert만을 확정 원인으로 단정하지 않는다.**

필요 작업은 단계별 시간·행 수·오류 기록, 쿼리 실행 계획 확인, 제한된 크기의 저장 배치, 실패한 배치 재개, 완료된 동일 집계 실행을 가리키는 공개 기준이다. 실행별 staging/run_id와 완료 후 공개 포인터 전환 등의 방식으로 미완료 결과가 섞이지 않게 한다. 스냅샷 갱신 시각과 지연 상태를 사용자에게도 표시한다.

수용 기준: 중간 쓰기에 실패를 주입해도 독자는 이전의 완료된 결과만 읽고, 성공한 다음 실행에서 실험체·조합·벤치마크가 같은 실행 기준으로 전환된다. 실제 데이터 규모에서 전체 집계와 재개를 확인한다.

### QA-003·QA-007. 선택한 범위가 계산까지 유지되어야 함

추천의 playerDataScope는 결과 라벨에는 전달되지만 getPlayerSummary와 collectPlayerSeasonProfile 호출은 season으로 고정되어 있다. 모의 실행에서 current_patch를 요청해도 조회한 scope는 season, 결과 라벨은 current_patch였다. 후보 선택·개인 성과·수집·캐시와 설명이 모두 같은 scope를 사용하도록 연결해야 한다.

티어표에서는 수집 전체를 선택한 카티야/저격총이 6,077판으로 표시됐다. 링크에 rankScope가 없어 상세에서는 기본 미스릴 이상 5,603판으로 바뀌었다. 링크와 상세 쿼리에 필터를 유지하고, 조합이 미스릴 이상만 제공된다면 별도 표본 기준을 명시한다.

근거: [추천 계산](../lib/recommendations.ts), [티어표](../app/characters/page.tsx), [실험체 상세](../app/characters/[code]/page.tsx).

### QA-004·QA-014. 패치 가져오기 기능을 사용 가능한 검수 흐름으로 완성

간단한 레온 변경 예제에서도 모든 character_code가 0이었다. 피해량 증가는 buff였지만 쿨다운 12→10 감소는 nerf가 됐다. 실험체 제목·스킬·무기 맥락을 보존하고, 지표별로 증가/감소의 유불리를 해석해야 한다. 레벨별 배열·계수·복합 변경도 별도 표본으로 검증한다.

현재 import는 note를 upsert한 뒤 변경 행을 insert하므로 재실행 시 중복 행이 쌓일 수 있다. reviewed=false로 저장해도 읽기 단계에 검수 완료 조건이 없다. 초안 미리보기→수동 보정→승인→공개 순서와 원자적 저장, 같은 원본의 재import 정책을 추가한다. 코드에 묶인 공식 변경 이력은 별도 구현이므로, 이번 파서 결함을 기존 이력 전체의 오류로 확대 해석하지 않는다.

근거: [파서](../lib/patch-notes.ts), [import API](../app/api/admin/patch-notes/import/route.ts), [데이터 조회](../lib/data.ts).

### QA-001·QA-002. 관리자 기능의 설정·URL 검증

ADMIN_TOKEN/CRON_SECRET이 없을 때 차단하도록 공통 인증을 정리하고, 환경별 실수 방지 검사를 추가한다. 관리자 통계 API는 이미 누락 시 차단하는 별도 처리가 있어 다른 관리 API와 동작이 다르다.

패치 URL은 현재 임의 URL을 서버 fetch에 전달하며 허용 도메인·프로토콜·리다이렉트 목적지·응답 크기·시간 제한이 없다. 모의 fetch로 비공식 loopback URL까지 전달되는 것을 확인했으며 실제 내부 주소에 접속하지 않았다. 공식 HTTPS 출처로 제한하고 리다이렉트와 최종 목적지를 검증한다.

### QA-006·QA-013·QA-026. 잘못된 입력과 근거 부족 상태를 명확하게 표시

- 잘못된 JSON은 추천·분석 API에서 500으로 분류됐다. 클라이언트 입력 오류로 처리해야 한다.
- 음수·소수·중복 팀원 코드와 소수 limit가 스키마를 통과했다. 유효 실험체 코드·정수·범위·고유성 검사를 추가한다.
- periodDays=bad는 NaN으로 조회 함수까지 전달됐다. 지원 기간만 받도록 정의한다.
- 메타가 전혀 없는 경우 평균 순위 0.00, 승률 0%가 관측 통계처럼 설명된다. 데이터 없음은 null/집계 대기 상태로 전달한다.
- 실제 팀원 2명 추천에서 직접 조합 표본이 없는 타지아가 신뢰도 높음으로 표시됐다. 상세 설명에는 조합 표본 부재가 안내되어 있었지만 첫 화면의 신뢰도는 메타 표본에 대한 것이었다. 메타·개인·조합 신뢰도를 나누고 표본 기준을 지표 옆에 표시한다.

나머지 성능·캐시·식별·오류 상태·문서·자동화 항목을 포함한 **28개 점검 항목의 상태와 완료 조건**은 [백로그](qa-backlog.md)에 정리했다. 코드상 위험이나 설계 개선은 운영 장애가 재현된 결함과 구분했다.

| F-10 | 근거 데이터 내보내기와 결과 공유 | 표본·패치·시각·계산 버전을 포함한 내보내기, 공유 범위 선택 | 현재 데이터로 가능. 재조회 가능한 결과 식별자 필요 | P3 |
| F-11 | 근거 기반 후속 질문형 코치 | 현재 분석 근거 내에서 답하고 부족한 데이터는 요청·보류. 수치와 후보는 서버 확정 | LLM은 선택. 복합 문답 품질 평가 후 상위 모델 검토 | 후속 확장 |
| F-12 | 교전·이동 경로와 영상 기반 피드백 | 실제 장면/타임라인을 받아 특정 순간의 판단을 설명 | 현 공개 문서에서 완전한 리플레이·이동 타임라인 API를 확인하지 못함. 별도 데이터 제공 가능성 확인부터 필요 | 데이터 확보 전 보류 |

F-03은 기존 캡처에서 equipment·skillOrderInfo·routeIdOfStart 등의 존재를 확인한 제안이다. API가 제공하는 원본과 ERPS가 현재 영구 저장하는 필드는 같지 않으므로 저장·표시까지 구현해야 한다. 오래된 문서에 있는 분당 크레딧 배열은 해당 캡처에서 없었으므로, 문서만 보고 실제 시계열 데이터가 항상 있다고 가정하지 않는다.

## 5. 어디에 상위 API가 필요한가

여기서 상위 API는 ① 게임 API 호출 한도 확대, ② 제한 필드 접근 권한, ③ 상위 LLM 모델/사용 한도, ④ 현재 공개 API에 없는 추가 데이터로 나눈다. 단순 API 버전 v1/v2 전환은 이 구분과 다르다.

### 5.1 게임 API: Production Key의 효과가 있는 곳

공식 개발자 포털의 Getting Started에는 Personal Key가 초당 1회, Production Key가 초당 50회로 안내되어 있으며, 공개 서비스 계획을 개발자 Discord에 설명해 신청하도록 되어 있다. **현재 프로젝트 키가 어느 종류인지와 실제 승인 한도는 확인하지 않았다.** 공개 안내가 구형 v1 설명도 포함하므로 실제 발급 조건과 한도는 제공자에게 재확인해야 한다. [공식 키 안내](https://developer.eternalreturn.io/getting-started)

| 사용 위치 | 필요한 기능 | 확대 판단 | 확대 전에 필요한 구현 |
| --- | --- | --- | --- |
| lib/ingestion.ts의 랭커 탐색, lib/eternal-return.ts의 user games·game detail 요청 | 넓은 표본 수집과 짧은 갱신 간격 | 현재 키가 개인용이고 대기열 지연의 주원인이 게임 API 한도라면 Production Key 우선 검토 | 키 전체를 공유하는 제한기, 제한된 동시성, 429/403 지표, 저장 처리량 점검 |
| collectPlayerSeasonProfile·collectPlayerAnalysisMatches | 첫 개인 조회, 여러 플레이어 동시 분석 | 동시 사용자가 늘어날 때 효과. DB 비교군 조회가 느린 경우 별도 개선 필요 | 작업 병합·캐시·우선순위 큐·진행 상태 |
| F-04의 실제 팀원 다중 프로필 추천 | 2~3명의 전적을 함께 갱신 | 조회량 증가에 따라 유효할 가능성이 큼 | 전체 재수집 대신 증분 갱신, 팀원별 캐시 재사용 |

현재 scheduledFetch는 프로세스 내부 Promise 큐이고 기본 요청 간격은 1,000ms다. 키만 바꿔도 50회/초 성능이 자동으로 나오지 않는다. 웹 서버·예약 수집기·여러 서버 인스턴스가 같은 키를 쓰는 경우의 합산 한도도 관리해야 한다. 불필요한 요청 제거와 저장 처리 속도가 함께 따라가야 한다.

### 5.2 MMR 필드 권한: 정확한 비교군과 랭크 필터의 전제

공식 명세는 mmrBefore/mmrAfter를 일부 API 사용자에게 제공하는 필드로 설명한다. 이 값은 랭크 범위·MMR 비교군·RP 해석에 연결된다. **Production Key의 호출량 확대와 해당 필드의 접근 권한이 동일하게 부여된다고 확인하지 않았다.** [공식 데이터 명세](https://developer.eternalreturn.io/static/media/OpenAPI_EN_20260917_01.html)

필요 위치는 lib/ingestion.ts의 저장 매핑, lib/rank-scopes.ts의 범위 분류, lib/player-analysis-cohort.ts와 lib/player-analysis.ts의 비교다. 현재 보관 캡처 일부에는 MMR 값이 있어 권한 부족을 확정할 수 없다. 최신 랭크 응답의 필드 존재율을 먼저 측정하고, 누락이 권한 때문일 때 제공자에게 필드 권한을 문의한다. 미제공 값을 실제 0 MMR로 간주하거나 임의로 정확한 경기 전후 값을 복원하지 않는다.

### 5.3 추가 게임 데이터: 높은 호출 한도만으로는 확보되지 않는 부분

공식 문서의 개인 경기 조회는 최근 90일이며 닉네임 변경 전 경기가 조회되지 않을 수 있다. UID도 닉네임 변경에 따라 달라질 수 있다고 안내한다. 장기 추적은 허용 범위의 자체 보관·사용자 확인과 식별 정책이 필요하다. 상위 키가 과거 전체 전적이나 영구 식별자를 제공한다고 가정하지 않는다. 완전한 실시간 교전·위치·리플레이 제공도 별도로 확인해야 한다. [공식 조회·식별 범위](https://developer.eternalreturn.io/static/media/OpenAPI_EN_20260917_01.html)

같은 공개 응답의 장비·스킬 순서·시작 루트 표시는 상위 API 구매보다 수집·저장·화면 구현의 문제다. 전체 랭크 모집단에 대한 통계를 제공하려면 랭커 중심 표집의 한계를 검토해야 하며, 요청량을 늘리는 것만으로 표집 편향이 사라지지는 않는다.

### 5.4 OpenAI: 현재 기능에는 상위 모델이 필수 아님

현재 추천 설명은 코드가 통계에서 직접 만든다. 개인 분석에서만 키가 있을 때 확정된 후보의 요약·보충 설명을 추가하고 실패 시 기본 설명으로 돌아간다. 이번 로컬 설정에는 OPENAI_API_KEY가 없었다. 배포 환경의 키 설정은 확인하지 않았다.

| 대상 | 현재 판단 | 권장 작업 |
| --- | --- | --- |
| 기존 추천 순위·통계·상대 점수 | 상위 모델 불필요 | 계산과 표본·필터 오류부터 수정 |
| 기존 분석의 짧은 한국어 보충 설명 | 상위 모델 필수 아님 | 현재 gpt-5-mini도 Structured Outputs 지원. 스키마 강제·출력 한도·검증 실패율 관측부터 적용 |
| F-11 복합 후속 질문·장기 상담·다중 근거 해석 | 상위 추론 모델 선택 가능 | 동일한 평가 표본으로 근거 이탈률·수치 보존·지연·비용을 비교한 뒤 채택 |
| 많은 사용자의 동시 AI 설명 | 모델 품질과 별개의 API 사용 한도 문제 | 조직/프로젝트/모델별 실제 제한과 429·토큰량·비용을 확인 후 한도 확대 검토 |
| F-12 장면 분석 | 텍스트 모델만 올리는 것으로 부족 | 영상·프레임 등 실제 입력과 검증 체계부터 확보 |

공식 명세상 gpt-5-mini는 Structured Outputs를 지원한다. 현재 lib/openai.ts는 JSON을 지시하고 사후 Zod 검증을 하지만 Responses의 text.format JSON schema는 지정하지 않는다. 모델 교체 이전에 개선할 수 있다. 구조화 출력도 내용의 진실성까지 보장하지 않으므로 서버의 후보·근거 검증은 유지한다. [모델 기능](https://developers.openai.com/api/docs/models/gpt-5-mini), [구조화 출력](https://developers.openai.com/api/docs/guides/structured-outputs)

또한 현재 timeout:5000은 요청 1회 기준이고 설치된 SDK의 기본 재시도는 2회다. 전체 보충 설명이 반드시 5초 안에 끝난다고 볼 수 없다. 총 지연 예산·재시도·fallback 측정이 필요하다. API 사용 한도는 모델 능력과 별개이며 조직·프로젝트와 모델별로 적용된다. [OpenAI 호출 한도](https://developers.openai.com/api/docs/guides/rate-limits)

### 5.5 Supabase·작업 서버: API 확대와 분리해서 판단

이번에 관측된 statement timeout과 닉네임 없는 추천의 15.7초 요청은 DB와 애플리케이션 경로를 먼저 조사해야 한다. 조회 컬럼·필터·페이지 정렬·집계 쿼리·배치 쓰기·캐시를 조정하고 실제 실행 계획과 부하를 측정한다. [Supabase 쿼리 최적화](https://supabase.com/docs/guides/database/query-optimization)

최적화 이후에도 CPU·메모리·연결·I/O가 한계이고 목표 응답 시간을 충족하지 못할 때 DB 자원 확대를 검토한다. 현재 요금제·실행 계획·자원 사용량을 조회하지 않았으므로 유료 업그레이드가 필요하다고 확정하지 않는다. 개인 PC에 의존하는 수집의 지속 실행은 워커·스케줄러 운영 환경의 문제이며 게임 API 권한이나 LLM 모델 등급과도 별개다.

## 6. API 확대를 결정할 측정 기준

| 결정 | 먼저 수집할 근거 | 확대 조건 |
| --- | --- | --- |
| 게임 Production Key | 키의 실제 한도, 요청 대기, 요청 수, 403/429 비율, 수집 지연, DB 저장 시간 | 중복 제거·캐시 이후에도 허용 호출량 때문에 수집/조회 목표를 충족하지 못함 |
| 제한 필드 권한 | 같은 시즌·모드의 필드 존재율, API 문서와 제공자 확인 | 제품에 필요한 값이 권한 때문에 제공되지 않음 |
| 상위 LLM 모델 | 근거 이탈률, 문구 채택률, 사용자 이해도, 전체 지연, 토큰 비용 | 기존 모델·스키마·근거 구성 개선 후에도 목표 품질을 충족하지 못함 |
| OpenAI 사용 한도 | 조직/프로젝트 제한, 동시 요청, TPM/RPM, 429 유형 | 모델 품질은 충분하고 실제 할당량이 병목임 |
| DB 자원/별도 워커 | 실행 계획, 단계별 시간, 동시 부하, CPU·I/O·연결과 배치 길이 | 쿼리·집계·캐시 개선 후에도 자원이 부족함 |
| 신규 타임라인 제공자 | 실제 데이터 샘플, 식별·패치·시간 정합성, 제공 범위 | 현재 공개 데이터로 기능의 필수 근거를 확보할 수 없음 |

목표 지연이나 비용 예산은 아직 합의된 값이 없다. 현재 관측값을 SLA로 삼거나, 특정 결제만으로 성능·분석 품질이 해결된다고 약속하지 않는다.

## 7. 권장 구현 순서

1. **데이터 신뢰성 복구**: QA-005 집계 단계 추적·배치·완료 결과 공개, QA-003 scope, QA-007 필터 유지, QA-013 데이터 없음 처리.
2. **관리 기능 완성**: QA-001 인증 누락 차단, QA-002 URL 제한, QA-004 파서, QA-014 검수·재import 정책, QA-006 입력 검증.
3. **실사용 안정화**: QA-012 DB 조회, QA-010/015 호출량 제어, QA-011 백그라운드 처리, QA-016/017/019 오류 상태, QA-020 통합 회귀.
4. **현재 데이터 활용 확대**: F-01 탐색, F-02 선택 픽 분석, F-03 경기 상세, F-06 점수 분해, F-07 운영 상태.
5. **사용량에 맞춘 API 확대**: 실제 키 한도와 병목을 확인한 뒤 Production Key, 제한 필드 권한, 워커/DB 자원을 순서대로 검토. F-04 팀 추천을 함께 설계.
6. **후속 제품 확장**: F-05 패치 추세, F-09 이력, F-11 코치. F-12 장면 분석은 데이터 제공 가능성부터 검증.

먼저 작업할 묶음은 QA-005 → QA-003 → QA-007 → QA-001/002/004다. 운영 데이터 재집계·마이그레이션·배포는 각각 로컬 변경과 검증 근거를 준비한 후 별도 실행 범위를 확정한다.
