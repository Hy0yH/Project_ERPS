# 데이터 수집 프로그램 보완점 검토

검토일: **2026-10-29 KST**. 대상 커밋: `f29f01cce75486455269560e3b4518c33274c810`.

후속 구현: 같은 날 [CHG-022](change-log.md#chg-022)에서 아래 주요 6개 항목의 코드·마이그레이션을 보완했다. 이 문서는 수정 전 조사 증거로 유지하며 현재 구현·검증·운영 상태는 [보완 기록](collection-reliability-2026-10-29.md)을 따른다.

## 결론

경기 큐·선점·중복 실행 차단·시간 제한·API 재시도·패치별 이어받기는 이미 구현돼 있다. 추가 보완의 우선순위는 **참가자 중복 방지와 경기 완료 판정 → 실패 경기 복구 → 실행 상태의 정확성 → 완료 집계의 일괄 공개**다. 정상 경로의 수집 속도를 높이기 전에 통계의 입력과 실패 복구를 보강할 필요가 있다.

이번 작업은 조사와 기록이다. 앱 실행 코드·환경 변수·예약 작업·운영 DB를 수정하거나 수집·재집계를 요청하지 않았다. 아래의 제안은 구현 완료 내역이 아니다.

### 1. 동일 참가자는 모든 경로에서 같은 키로 저장

`resolvePlayerUserNum()`은 개인 조회 대상이면 닉네임 해시를 우선하지만, 정기 수집에서는 공식 번호 또는 UID 해시를 우선한다. 기본키는 `(game_id, user_num)`이므로 같은 UID도 다른 행이 된다. 기존 정리는 개인 저장 경로에만 있어, **개인 부분 저장 → 정기 전체 저장** 순서의 중복을 막지 못한다.

확인된 공식 식별자와 내부 사용자 ID의 대응을 한곳에서 관리하고 모든 저장 경로가 이를 사용하도록 통일하는 것이 좋다. UID 형식 변경과 식별자 미제공은 명시적으로 처리해야 한다. 단순히 닉네임을 고유 사용자로 간주하거나 과거 UID 자료를 무조건 삭제해서는 안 된다. 기존 [ERPS-025](issue-log.md#erps-025)의 조회 보완과는 다른 저장 중복 문제다.

수정 검증 조건: 개인→정기 및 정기→개인 순서, 재수집, UID/번호 유무, 닉네임 변경에서 경기별 참가자가 중복되지 않을 것. 기존 중복 여부 감사와 정리 범위는 코드 수정 후 별도로 결정한다.

### 2. 개인 부분 저장과 경기 전체 수집 완료를 구분

개인 분석은 의도적으로 `saveGame({ gamePlayers: [row] })`를 호출한다. 그런데 완료 판정 함수들은 분석·상세 버전 조건을 만족하는 참가자 **8행 이상**이면 경기 전체가 준비됐다고 판단한다. 서로 다른 8명의 부분 저장만으로도 정기 큐가 상세 API를 호출하지 않고 완료될 수 있다.

고정 인원수를 24로 바꾸는 방법도 충분하지 않다. 실제 경기 인원수는 다를 수 있으므로 **전체 상세 응답을 검증·저장했다는 경기 단위 상태와 기대 참가자 수**를 보관하고, 개인 행 추가만으로 그 상태가 완료되지 않게 해야 한다. 경기·참가자·전체 저장 완료 표시를 한 트랜잭션으로 처리하면 중간 쓰기 실패도 분리할 수 있다. 전체 응답 내 사용자 중복·서로 다른 경기 ID 혼입도 함께 검사한다.

### 3. 재시도 소진을 별도 상태로 노출하고 복구 경로 제공

큐 조회와 대기 수 집계는 `attempts <= 3`만 포함하며 선점 시 횟수를 1 늘린다. 따라서 최대 네 번 실패한 행은 `failed, attempts=4`로 남지만 이후 처리와 `pendingMatches`에서 빠진다. 중복 발견도 `ignoreDuplicates` 때문에 이를 재개하지 않는다. 관리자 화면에는 전체 failed 수가 보일 수 있지만 자동 재처리와 소진 건수 구분은 없다.

`next_retry_at` 기반 지수 지연과 일시 오류/영구 오류 구분, `dead_letter` 또는 재시도 소진 분류, 소진 사유·건수·가장 오래된 미처리 시각을 제공하는 것이 좋다. 관리자가 선택한 건만 재개할 수 있도록 하고, 모든 실패의 횟수를 매번 초기화하는 무한 재시도는 피한다.

### 4. 실행 상태와 실패 진단의 신뢰성 확보

수집의 성공·실패 종료 UPDATE는 반환된 `error`를 검사하지 않는다. 오류를 주입했을 때 수집 결과는 반환됐지만 실행 행은 `running`에 남았다. 강제 종료도 종료 기록을 남기지 못하며 heartbeat·lease·중단 상태 정리는 없다. 운영의 오래된 기록 13건의 개별 원인은 미확인이다.

종료 저장 오류를 확인하고, 실행 ID·단계·최근 heartbeat·진행 건수를 기록하는 것이 좋다. 소유 실행의 lease가 만료되면 중단 상태로 구분하고, 과거 실행 행을 실제 작업 잠금의 유일한 근거로 사용하지 않는다.

또한 랭커 루프의 `catch`는 오류를 건수로만 남기고 전부 실패해도 `success`를 저장한다. `partial_success`와 실패 기준을 정의하고, 원본 예외 전체 대신 비밀값을 제거한 단계·오류 코드·재시도 가능 여부를 기록한다. 관리 화면의 `hasWarnings`만으로는 원인 구분이 어렵다.

### 5. 집계 전체가 완료됐을 때 결과 공개

실험체→조합→벤치마크를 순서대로 기존 행에 upsert하고 읽기에서는 각 테이블의 최신 시각을 찾는다. 배치 저장과 실패 진단은 개선됐지만, 중간 배치나 후속 테이블이 실패하면 이미 저장된 앞부분을 되돌리는 구조는 없다. 캐시 무효화도 실패 경로에서 수행한다.

`snapshot_run_id`별로 새 결과를 준비하고 검증 완료 후 공개 포인터를 한 번 전환하는 방식이 적합하다. 실패 시 마지막으로 완료된 집계를 유지하고, 재시도 시 실패 실행의 준비 데이터만 정리·재개하도록 한다. 상세 증상·과거 운영 장애는 기존 ERPS-006에 누적한다. 여러 Supabase 요청을 한 트랜잭션으로 묶을 필요가 있으면 DB 함수/RPC 등 DB 측 경계를 사용해야 한다([공식 설명](https://supabase.com/docs/reference/javascript/using-modifiers-rollback)).

## 후속 설계 개선

다음은 이번에 운영 장애로 확정한 항목이 아닌 예방·확장 제안이다.

- **공유 요청 제한과 실행 lease:** API 간격·Retry-After·지수 지연은 프로세스 내부에서 적용된다. 웹 개인 분석과 로컬 수집기가 같은 키를 쓰면 합산 제한을 보장하지 않는다. [QA-010](qa-backlog.md)의 후속으로 키 단위 공유 제한기와 개인 조회 우선순위를 검토한다. 큐의 조건부 선점은 유효하지만 랭커 탐색·체크포인트·집계 잠금까지 인스턴스 전체에서 보장하지는 않는다.
- **탐색 페이지 단위 보존:** 한 랭커의 여러 페이지를 함수 메모리에 모은 뒤 큐와 체크포인트를 저장한다. 중간 API 오류나 강제 종료 시 해당 호출에서 모은 페이지를 다시 조회한다. 페이지를 DB 큐에 저장한 뒤 같은 처리 경계에서 다음 커서를 보존하도록 개선할 수 있다. 로컬 JSON 체크포인트의 백업·내용 검증·서버 이동 시 이어받기도 함께 검토한다.
- **최신성·범위 지표:** 현재의 성공 횟수 외에 최근 경기 시작 시각→저장 시각 지연, 최초 큐 발견→완료 지연, 재시도 소진·가장 오래된 대기, 티어별 고유 사용자·경기·시간대 분포를 보자. 상위 랭커 중심 탐색으로 수집한 하위 티어 통계는 해당 티어 전체의 무작위 표본을 의미하지 않는다. 목표 모집단과 표본 범위를 화면에서 설명할 필요가 있다.
- **입력 검증:** 날짜 파싱 실패를 현재 시각으로 대체하는 경로, 수치 환경 변수의 음수·소수 허용, 상세 버전을 필드 존재만으로 부여하는 기준을 보강한다. 유효하지 않은 원본은 사유와 함께 격리하고 전체 경기 완료와 분리한다.

## 재현과 제한

아래 명령은 수정 전 대상 커밋에서 문제를 재현하는 조사 자료다. 현재 수정 코드에서 REVIEW 검사의 잘못된 동작 기대값이 실패하는 것은 정상이다. 수정 후 검증에는 `pnpm test`의 회귀 검사를 사용한다.

```powershell
node docs/evidence/collection-review-probes-2026-10-29.cjs
pnpm exec vitest run --config .scheduler/collection-review.vitest.mjs
```

재현 스크립트는 대상 커밋의 기존 파이프라인 모의 DB 검사를 바탕으로 `.scheduler`에 검사 파일과 설정만 만든다. 공식 API와 Supabase는 모의 구현으로 교체하며 실제 DB 쓰기·수집 요청·예약 작업 변경은 없다. 각 REVIEW 검사는 **현재의 잘못된 동작이 발생하는지** 확인하는 조사 자료다. 수정 이후에는 올바른 기대값을 가진 회귀 검사로 바꿔야 한다.

운영 전체 이력의 UID 중복·모든 경기 참가자 완전성·대규모 집계 부하·다중 인스턴스 충돌·Windows 다음 예약 실행·브라우저 화면은 이번 검증 범위가 아니다. 실제 측정이 없는 처리량 향상 수치는 제시하지 않는다.
