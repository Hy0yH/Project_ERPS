# ERPS 문제·버그 기록

사이트에서 발견한 버그, 성능 저하, 운영 오류와 해결 과정을 계속 누적하는 문서다. 각 항목에는 **무슨 문제가 있었는지, 왜 발생했는지, 왜 그 방법을 선택했는지, 어떻게 수정하고 확인했는지**를 남긴다.

최종 갱신일: 2026-10-29 KST.

기능 추가·개선·정책·UI·운영 변경은 [기능 추가·변경 이력](change-log.md)에 따로 기록한다. 이 문서는 의도한 동작을 벗어난 문제의 증상·원인·수정·검증을 관리한다. 기능 변경과 관련된 버그는 ID로 서로 연결하고, 기존 상세 기록은 유지한다.

## 기록 방법

- 새 문제는 목록과 상세 기록에 함께 추가한다. ID는 `ERPS-001`부터 순서대로 부여하고 삭제하거나 재사용하지 않는다.
- 목록과 상세는 **KST 기준 오래된 날짜 → 최신 날짜** 순서로 맞춘다. 정렬 기준일은 최초 확인일이며, 발견일이 없으면 확인된 최초 수정 이력일을 사용한다. 여러 이력일이 있으면 첫 날짜, 같은 날짜면 ID 오름차순, 날짜 미확인이면 마지막에 배치한다.
- ID·앵커는 날짜 정렬과 관계없이 유지한다. 새 ID는 문서 전체의 최대 번호 다음으로 부여하고 해당 날짜 위치에 삽입한다. 각 항목의 후속 이력도 날짜순으로 유지한다.
- 동일 문제의 추가 조사·수정·배포·재발은 해당 항목의 진행 이력에 날짜와 함께 추가한다. 기존 측정과 판단은 당시 기록으로 보존한다.
- 해결 상태는 `접수`, `조사 중`, `수정 중`, `수정 완료`, `운영 확인 완료`, `보류`로 표시한다. 운영 반영은 `미배포`, `배포 완료`, `적용 불필요`, `미확인`으로 별도 표시한다.
- 원인이 확정되지 않았다면 가설과 남은 확인을 구분한다. 미실시한 검증은 통과로 기록하지 않는다.
- 측정값에는 환경·대상·지표·측정일을 함께 적는다. 단일 측정과 반복 측정, 로컬 결과와 운영 결과를 구분한다.
- 자세한 증거가 별도 문서에 있으면 여기에 핵심 내용을 요약하고 링크로 연결한다.

기존 QA 항목은 [QA 백로그](qa-backlog.md)에 QA-001~QA-028 번호로 정리되어 있다. 이전 구현·검증 과정은 [QA 진행 기록](qa-progress.md)을 참고한다. 기존 항목을 다시 다룰 때는 원래 QA ID도 연결한다.

2026-10-28에 과거 QA·수치 검증 문서와 Git 수정 이력에서 근거가 확인되는 문제 26건을 추가했다. 아래 과거 항목의 상태는 해당 문서·커밋에서 확인한 범위이며, 이번 기록 작업에서 버그를 다시 실행하거나 운영 배포를 확인한 것은 아니다. 발견일을 알 수 없는 항목은 수정 이력일을 표시한다. 수정 커밋만으로 운영 반영 완료를 추정하지 않는다. 코드상 위험·기능 제안만 있고 결함 재현이 없는 QA 항목은 확정 버그로 옮기지 않았다.

### ERPS-015 — 저장 전적 의존과 오래된 값의 최신 원본 덮어쓰기

정렬 기준일: **2026-09-07 KST**.

- **관련 이력·상태:** 최초 발견일 미상. 2026-09-07 공식 응답 직접 분석 보완 → 10-26 최신 원본 우선순위·정렬 개선 → 10-28 등록. 수정 완료, 운영 반영 미확인.
- **증상·재현:** 공식 API에서 이미 얻은 경기가 있어도 저장 전적 조회가 늦거나 누락되면 분석에서 빠질 수 있었고, 같은 경기의 오래된 저장 값이 최신 응답보다 우선할 수 있었다. 시각 문자열 형식이 다르면 최신 50판 정렬도 어긋날 수 있었다.
- **원인:** 분석 입력을 저장 조회 결과에 의존하고, 병합 우선순위·문자열 정렬이 실제 최신성을 충분히 보장하지 않았다.
- **왜·어떻게 해결:** 확보한 공식 전적을 저장 기록과 병합하되 동일 경기는 최신 공식 응답을 우선한다. 저장·비교군 조회 실패 시에도 확보한 실제 통계를 유지하고, 시각은 실제 타임스탬프로 정렬한다.
- **검증:** 최신 공식 값 우선, 저장·비교군 시간 초과, UTC·KST 혼합 정렬 회귀 검사가 있다. [서비스 검사](../tests/player-analysis-service.test.ts), [정렬 검사](../tests/player-analysis.test.ts).
- **남은 확인:** 운영 DB 장애 시의 응답과 표본 범위. 과거 UID 조회 누락은 ERPS-025와 별도 원인이다.
- **근거:** [수정 커밋 2b775e7](https://github.com/Hy0yH/Project_ERPS/commit/2b775e73ca549abc6abb2c81bd8b2c16287d432b), [수치 검증](player-analysis-validation-2026-10-26.md).

### ERPS-024 — 오래된 설정으로 인한 패치 자동 전환 실패

정렬 기준일: **2026-09-07 KST**.

- **관련 이력·상태:** 발견일 미상, 2026-09-07 수정 커밋 확인 → 10-28 등록. 수정 완료, 운영 반영 미확인.
- **증상·재현:** 설정에 12.2가 남고 저장된 최신 패치가 12.3이어도 설정 패치만 사용했다. 수집 중 새 패치가 발견돼도 분석이 이전 선택을 유지할 수 있었다.
- **원인:** 유효한 패치 설정을 무조건 우선하고 수집 이후 활성 패치를 다시 확인하지 않았다.
- **왜·어떻게 해결:** 설정과 저장된 최신 패치를 비교해 오래된 설정보다 최신을 사용하고, 수집 후 패치를 다시 확인해 분석·비교·결과 범위를 맞췄다. 의도적으로 지정한 최신 설정은 보존한다.
- **검증:** 해당 커밋에 오래된 설정·현재/미래 설정·설정 없음의 선택 검사가 추가됐다. 당시 실행 결과와 운영 검증 기록은 이 커밋만으로 확인하지 못했다. [패치 검사](../tests/patch-version.test.ts).
- **남은 확인:** 새 패치마다 시작 경계·설정·분석 캐시 범위를 함께 점검한다.
- **근거:** [수정 커밋 a0cb8cf](https://github.com/Hy0yH/Project_ERPS/commit/a0cb8cf90f65286358fd6a279800b770ba1e9b68).

### ERPS-025 — 공식 UID 형식 변경 후 과거 전적 조회 누락

정렬 기준일: **2026-09-07 KST**.

- **관련 이력·상태:** 발견일 미상, 2026-09-07 수정 커밋 확인 → 10-27 감사에서 관련 식별 문제 관측 → 10-28 등록. 서비스 조회 보완 완료, 운영 반영 미확인.
- **증상·재현:** 현재 공식 UID로 저장 전적을 찾지 못하지만 당시 닉네임으로는 과거 행을 찾을 수 있었다. 10-27 저장 전적 감사에도 닉네임 보완 조회가 필요했다.

### ERPS-001 — 메인 화면 첫 접속 지연

정렬 기준일: **2026-10-28 KST**.

| 항목 | 내용 |
| --- | --- |
| 접수일 | 2026-10-28 KST |
| 대상 | 메인 경로 `/`, 최초 접속 |
| 해결 상태 | 코드 수정·로컬 검증 후 운영 메인 응답 확인 완료 |
| 운영 반영 | 1679a5d를 Test → main에 반영하고 Vercel 운영 배포 READY·실제 도메인 응답 확인 |
| 관련 기록 | QA-012의 홈 전체 조합 조회 병목과 연결. 추천 API 전체의 성능 개선까지 완료한 것은 아님 |
| 상세 증거 | [첫 접속 지연 측정·수정 기록](home-loading-performance-2026-10-28.md) |

#### 증상과 영향

사용자가 사이트 주소로 처음 접속할 때 화면이 나오기까지 오래 기다렸다. 운영 사이트의 단일 GET 측정에서 HTTP 200 응답의 첫 바이트까지 **33.334301초**, 전체 수신까지 **33.352884초**가 걸렸다.

예상 동작은 메인 화면의 티어표 바로가기와 닉네임 입력창을 빠르게 제공하는 것이다. 기존 구조에서는 통계 조회를 끝내기 전까지 이 화면들도 기다렸다.

#### 재현·확인 방법

1. 사이트 주소 `https://project-erps.vercel.app/`로 직접 접속한다.
2. 브라우저 Network의 문서 요청에서 첫 응답 대기 시간과 캐시 헤더를 확인한다.
3. 조사 당시에는 `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate`와 `X-Vercel-Cache: MISS`가 확인됐다.

운영 응답은 2026-10-28 00:17 KST경의 단일 측정이다. 이후 접속에서도 같은 시간이 보장되는 것은 아니다.

#### 원인

| 확인한 구조 | 지연으로 이어진 이유 |
| --- | --- |
| 상위 조합 5개를 표시하기 위해 전체 조합 32,667개를 조회하고 이름을 붙여 정렬 | DB 응답량과 페이지를 나눠 읽는 요청 수가 커짐 |
| 메인 페이지의 `dynamic = "force-dynamic"` 설정 | 방문할 때마다 서버가 DB를 읽고 화면을 다시 생성 |
| 페이지에서 통계 조회를 먼저 `await` | 조회 완료 전에는 바로가기와 닉네임 입력 영역도 표시되지 않음 |
| 패치·최신 스냅샷·조합 count의 반복 조회 | 같은 화면을 만드는 동안 공통 정보를 여러 번 읽음 |
| 공개 갱신 상태에 관리자용 조회 함수를 사용 | 필요하지 않은 대기열 count, 벤치마크와 수집 실행 로그까지 조회 |

각 원인이 전체 33.3초에서 차지한 비율은 개별 측정하지 않았다. 배포 함수의 `iad1` 실행 리전도 관측했지만 Supabase DB 리전과의 지연을 분리 측정하지 않았으므로 확정 원인으로 판정하지 않았다.

#### 해결 이유와 방법

| 조치 | 선택한 이유와 적용 방식 |
| --- | --- |
| 메인 화면에 `revalidate = 60` 적용 | 모든 방문자가 공유하는 통계 화면을 사전 렌더링하고 캐시된 HTML을 재사용하도록 함. 60초 후 요청 시 갱신하는 구조로 변경 |
| 통계를 비동기 컴포넌트로 분리하고 `Suspense` 적용 | 캐시가 없는 렌더링에서도 통계를 기다리는 동안 바로가기와 입력창을 먼저 제공 |

- **해결 이유·방법:** 실험체 기본 정보에서 요청 무기의 사용 가능 여부를 검증해 통계가 없어도 해당 무기를 유지한다. 잘못된 요청은 실험체의 첫 번째 지원 무기를 사용한다. 제목도 기본 이름과 무기 이름으로 보완했다. 수정 파일: [상세 화면](../app/characters/[code]/page.tsx).

- **증상·사용자 영향:** `collect-scheduled.ps1 -DryRun`이 예제 `CRON_SECRET`이나 `ADMIN_TOKEN`만 있는 설정을 정상으로 표시한다. 실제 수집 요청은 수집 API의 503/401 차단으로 실패해, 운영자가 사전 검사 결과를 믿고 수집을 시작할 수 있다.
- **재현·확인:** Windows PowerShell의 격리 프로젝트 사본에 가짜 설정을 넣어 검사했다. 수정 전 예제 수집 인증값·관리자 토큰만 설정·빈 수집 인증값과 관리자 토큰의 3개 경우 모두 종료 코드 0과 정상 안내가 나왔다. 외부 API/DB는 호출하지 않았다.
- **확인된 원인:** 사전 검사는 인증값의 존재만 확인했고 런타임은 `CRON_SECRET`이 없으면 `ADMIN_TOKEN`으로 대체했다. 반면 [수집 API 인증](../lib/auth.ts)은 유효한 `CRON_SECRET`만 비교하고 미설정·예제값은 차단한다. API의 보호 동작 자체는 정상이며 [ERPS-002](#erps-002)와 구분한다.
- **해결 이유·방법:** [예약 스크립트](../scripts/collect-scheduled.ps1)에 공통 수집 인증값 검사를 추가해 사전 검사와 실제 실행 모두 비어 있지 않은 비예제 `CRON_SECRET`을 요구한다. 관리자 토큰 대체는 제거하고 서버 시작·HTTP 요청 전에 잘못된 설정을 명확한 오류로 중단한다. 비밀값은 출력하지 않는다.
- **검증 결과:** 유효 인증값·따옴표로 감싼 유효값은 통과하고 예제값·관리자 토큰만 설정·빈 값과 관리자 토큰·완전 누락은 실패하는 격리 검사 6개가 모두 통과했다. 실제 로컬 설정의 `-DryRun`도 통과했다. 앱 전체 39파일 251테스트·타입 검사, 로컬/운영 상세 API의 12.7.0 응답과 잘못된 입력 400·잘못된 수집 토큰 401을 확인했다. [검증 근거](evidence/collection-release-validation-2026-10-29.json).
- **남은 작업·한계:** 현재 수집 인증값은 앞선 운영 재개 때 정상 값으로 설정됐다. 이번 변경 후 스크립트 전체의 다음 예약 실행은 아직 대기 중이며, 최초 75경기 집계 성공과 수정된 사전 검사 검증을 구분한다. 큰 표본의 시간 초과는 [ERPS-006](#erps-006)의 별도 미검증 범위다.
- **진행 이력:** 2026-10-29 KST — 커밋 전 오류 검증에서 3가지 잘못된 설정의 정상 오판정을 재현 → 공통 검사·대체 제거 → 격리 6개·실제 설정 사전 검사 통과. [CHG-020](change-log.md#chg-020)에 운영 변경을 연결한다.

### ERPS-034 — 재시도 소진 경기의 자동 복구·대기 집계 누락

정렬 기준일: **2026-10-29 KST**. 분류: 운영. 상태: **수정 완료·운영 미배포**.

- **증상·사용자 영향:** 일시적인 상세 조회 오류가 네 번 이어지면 장애가 끝나도 해당 경기는 자동 수집되지 않는다. 이후 실행의 `pendingMatches`·`failedMatches`가 모두 0이어도 실패 행은 남을 수 있다. 관리자 전체 failed 수와는 구분한다.
- **재현 조건:** 하나의 경기 상세 조회를 계속 실패시키고 수집을 5회 실행한다. 상세 호출은 4회, 행은 `failed/attempts=4`, 5회차 실패·대기 건수는 0이었다.

- **초기 조사 시 남은 작업:** 429·5xx·연결 장애·영구 오류별 정책, 소진 알림·선택 재개, 코드 수정·운영 검증.
- **진행 이력:** 2026-10-29 KST — 재시도 소진과 집계 제외를 격리 재현하고 접수. 운영 실패 행 재개는 하지 않음.
- **후속 수정·로컬 검증 — 2026-10-29 KST:** attempts 상한 필터를 제거하고 next_retry_at 기반 지연 재시도와 영구 HTTP 오류의 dead_letter 상태를 추가했다. 재시도 대기 행은 대기 수에 포함하며 관리자 인증이 필요한 선택 재개 API/UI를 구현했다. 5회차 처리·냉각 중 건수·영구 오류 분리·선택 재개와 처리 중/완료 보존 검사가 통과했다. 전체 43파일·294테스트·타입 검사·별도 프로덕션 빌드 검증을 완료했다. [CHG-022](change-log.md#chg-022), [검증 증거](evidence/collection-reliability-validation-2026-10-29.json).
- **현재 남은 작업:** 새 마이그레이션 적용·새 코드 배포·운영 수집/집계 확인. 현재 상태는 로컬 수정 완료이며 운영에서 해결된 것으로 기록하지 않는다.

### ERPS-035 — 수집 종료 기록 오류 무시와 오래된 실행 상태 잔존

정렬 기준일: **2026-10-29 KST**. 분류: 운영. 상태: **수정 완료·운영 미배포**.

- **증상·사용자 영향:** 수집이 결과를 반환했어도 실행 기록이 running에 남을 수 있다. 오래된 기록만으로 관리자가 실제 실행 중·중단·종료를 구분하기 어렵다.
- **재현 조건·운영 관측:** 수집 종료 UPDATE가 오류를 반환하도록 주입하면 저장 1건의 결과는 정상 반환하지만 실행 행은 running·종료 시각 없음으로 남았다. 별도로 20:34~20:36 KST 읽기 전용 조회에서 4시간 이상 running인 collect-rankers 기록 13건을 확인했다.
- **확인된 원인:** 수집 성공·실패 UPDATE의 반환 error를 검사하지 않는다. heartbeat·실행 lease·강제 종료 후 상태 정리도 없다. **운영 13건의 개별 원인은 미확인**이며 종료 UPDATE 오류인지 강제 종료인지 등은 가설이다. 실제 프로세스 생존 여부도 이 조회로 확인하지 않았다.
- **초기 조사 당시 제안:** 종료 기록 오류 확인과 별도 진단, heartbeat·lease, 만료 실행의 interrupted/abandoned 분류를 제안한다. 오래된 행을 삭제하거나 임의로 success 처리하지 않는다.
- **검증 결과:** 모의 DB REVIEW-4 재현 통과, 운영의 오래된 기록 관측. 운영 행 수정·프로세스 종료는 하지 않았다.
- **초기 조사 시 남은 작업:** 실행 소유권·중단 판정 정책, 강제 종료/DB 오류 검사, 코드 수정·배포·운영 상태 확인.
- **진행 이력:** 2026-10-29 KST — 종료 기록 오류 재현 및 오래된 실행 기록의 읽기 전용 관측, 접수.
- **후속 수정·로컬 검증 — 2026-10-29 KST:** DB 시작/heartbeat/종료 RPC로 소유권·저장 오류를 확인하고 30초 heartbeat·10분 lease를 추가했다. 후속 실행은 만료된 실행을 interrupted로 분류하고 그 실행이 선점한 큐만 회수한다. 종료 오류 시 성공 반환 금지·heartbeat 상실·타이머 종료·lease 만료/큐 회수 검사가 통과했다. 과거 운영 13건을 임의 수정하거나 원인을 확정하지 않았다. 전체 43파일·294테스트·타입 검사·별도 프로덕션 빌드 검증을 완료했다. [CHG-022](change-log.md#chg-022), [검증 증거](evidence/collection-reliability-validation-2026-10-29.json).
- **현재 남은 작업:** 새 마이그레이션 적용·새 코드 배포·운영 수집/집계 확인. 현재 상태는 로컬 수정 완료이며 운영에서 해결된 것으로 기록하지 않는다.
- **관련 기록:** [검토](collection-review-2026-10-29.md), [증거](evidence/collection-review-2026-10-29.json), [재현 스크립트](evidence/collection-review-probes-2026-10-29.cjs).

<a id="erps-036"></a>

### ERPS-036 — 랭커 탐색 전체 실패를 성공 실행으로 기록

정렬 기준일: **2026-10-29 KST**. 분류: 운영. 상태: **수정 완료·운영 미배포**.

- **증상·사용자 영향:** 선택된 랭커의 전적 탐색이 모두 실패하고 저장도 0건인데 실행은 success로 기록된다. 성공 상태나 HTTP 성공 여부만 사용하는 감시는 수집 장애를 놓칠 수 있다.
- **재현 조건:** 선택 랭커 1명의 전적 조회를 실패시키면 failedRankers=1·savedMatches=0·실행 status=success가 된다. 실패 건수 경고는 남으므로 오류가 전혀 기록되지 않는다는 의미는 아니다.
- **확인된 원인:** 랭커 루프 catch가 원인 없이 실패 건수만 증가시키고, 루프 이후 성공/부분 성공/전체 실패를 구분하지 않고 success를 저장한다. 관리 화면도 수집 오류는 주로 `hasWarnings` 여부만 표시한다.
- **초기 조사 당시 제안:** 기존 큐 처리 성공·시도한 탐색·실패 비율을 고려한 상태 기준과 partial_success를 정의하고, 단계·정제된 오류 코드·재시도 가능 여부를 기록한다. 단순 신규 경기 0건인 정상 실행과 장애를 구분한다.
- **검증 결과:** 모의 DB REVIEW-3 재현 통과. 최근 운영 실행 313은 오류 경고 없이 정상 성공했으며, 현재 탐색 장애가 발생 중이라고 단정하지 않는다.
- **초기 조사 시 남은 작업:** 정상 0건·일부 실패·전체 탐색 실패·큐 일부 성공의 상태 기준 검증, 오류 노출 범위·알림 연결, 코드 수정·배포.
- **진행 이력:** 2026-10-29 KST — 전체 실패의 성공 분류를 격리 재현하고 접수. 코드 수정·운영 쓰기는 없음.
- **후속 수정·로컬 검증 — 2026-10-29 KST:** 실제 탐색 성공 건수와 큐 처리 결과로 success/partial_success/failed를 구분하고 전체 실패는 HTTP 503으로 반환한다. 오류는 정제된 단계·코드·건수로 기록하며 관리자 화면에 진단과 중단/일부 실패를 표시한다. 전체 실패 분류·HTTP 상태와 오류 문자열 비노출 검사가 통과했다. 전체 43파일·294테스트·타입 검사·별도 프로덕션 빌드 검증을 완료했다. [CHG-022](change-log.md#chg-022), [검증 증거](evidence/collection-reliability-validation-2026-10-29.json).
- **현재 남은 작업:** 새 마이그레이션 적용·새 코드 배포·운영 수집/집계 확인. 현재 상태는 로컬 수정 완료이며 운영에서 해결된 것으로 기록하지 않는다.
- **관련 기록:** [검토](collection-review-2026-10-29.md), [증거](evidence/collection-review-2026-10-29.json), [재현 스크립트](evidence/collection-review-probes-2026-10-29.cjs).

## 새 항목 작성 양식

아래 양식을 복사해 문제 목록과 상세 기록의 같은 날짜 위치에 추가한다. `ERPS-NNN`은 문서 전체의 최대 번호 다음으로 부여한다. 현재 다음 번호는 `ERPS-037`이며, 문서 마지막에 있는 ID를 기준으로 번호를 정하지 않는다.

```markdown
<a id="erps-nnn"></a>

- 정렬 기준일: YYYY-MM-DD KST (최초 확인일 또는 발견일 미상 시 최초 수정 이력일)
- 접수일: YYYY-MM-DD KST
- 분류: 버그 / 성능 / 운영 / 보안 / 문서
- 대상: 화면·경로·기능
```
