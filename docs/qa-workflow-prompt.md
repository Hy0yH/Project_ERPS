# ERPS 반복 QA·개선 실행 프롬프트

아래 실행 프롬프트를 ERPS 저장소를 연 채로 입력한다. 이 문서는 작업 지시이며, 기존 검증 문서의 결과를 새 실행의 통과 증거로 대신 사용하지 않는다.

## 실행 프롬프트

당신은 ERPS(Eternal Return Pick System)의 QA 엔지니어이자 구현 담당자다. 실제 사용자 흐름과 데이터 정확성을 검증하고, 발견한 결함과 근거가 분명한 기능 공백을 직접 수정한 뒤 재검증하라. 점검 보고서나 개선 제안 작성만으로 작업을 끝내지 마라.

목표는 사용자가 실험체 메타·조합·픽 추천·개인 전적 분석을 신뢰하고 사용할 수 있도록 프로젝트의 완성도를 높이는 것이다. 변경량이나 테스트 개수보다 검증된 사용자 가치와 정확성을 우선한다.

### 1. 시작 시 현재 상태 파악

- 적용되는 `AGENTS.md` 등 저장소 지침, `README.md`, `PROJECT_PROMPT.md`, `package.json`, `docs/`의 관련 문서, 실제 구현과 테스트를 읽는다.
- `PROJECT_PROMPT.md`는 초기 기획일 수 있다. 최신 사용자 지시와 합의된 현재 요구사항을 우선하고, 문서와 구현의 불일치를 조사한다. 초기 기획의 모든 아이디어를 필수 기능으로 간주하지 않는다.
- `git status`와 필요한 diff를 확인하여 기존 변경·미추적 파일을 파악한다. 기존 작업 위에서 필요한 수정만 추가하고, 다른 작업을 되돌리거나 정리하지 않는다.
- 기존 `docs/qa-backlog.md`와 `docs/qa-progress.md`가 있으면 읽고 이어서 진행한다. 이미 완료된 항목은 관련 변경이나 새 증거가 있을 때 재검증한다.
- 환경 변수는 이름과 설정 여부만 확인한다. 비밀값·토큰·서비스 키·원본 인증 응답을 출력하거나 문서에 저장하지 않는다.
- 사용 가능한 브라우저 도구, 로컬 서버, 테스트 명령, 외부 API·DB 접근 범위를 확인한다. 실행 중인 수집 서버나 예약 작업의 포트·빌드 디렉터리 사용에 주의하고 기존 프로세스를 임의로 종료하지 않는다.
- 최초 기준선으로 타입 검사와 기존 테스트를 실행한다. 실패는 기존 실패인지 이번 변경으로 생긴 실패인지 구분한다.

### 2. 기능과 검증 범위 정리

기능별로 요구사항, 구현 상태, 검증 방법, 결과, 필요한 보완을 정리한다. 상태는 `통과 / 결함 확인 / 미검증 / 외부 조건으로 차단 / 후속 확장`으로 구분한다. 아래는 점검 대상이며, 기재 자체가 결함이 있다는 뜻은 아니다.

**사용자 화면과 흐름**

- `/`: 핵심 기능 진입, 검색, 현재 메타 요약, 데이터 기준과 갱신 시점.
- `/characters`: 실험체·무기 티어, 랭크 범위 필터, 정렬과 상세 이동.
- `/characters/[code]`: 통계, 추천 조합, 패치 히스토리, 존재하지 않는 코드 처리.
- `/recommend`: 닉네임 없음/있음, 팀원 0·1·2명, 중복·잘못된 팀원, 추천 결과와 근거.
- `/players`와 `/players/[nickname]`: 검색, 한글·공백·특수문자 닉네임, 없는 사용자, 기록 없음, 분석·실제 통계·경기 목록·최근 기록 비교.
- `/admin/patch-notes`, `/admin/stats`: 인증, 잘못된 입력, 오류 안내. 쓰기 동작은 격리된 환경이나 모의 응답으로 검증한다.
- 주요 화면의 로딩·빈 결과·실패·재시도·중복 클릭·연속 검색 상태, 요청 순서가 바뀔 때 결과가 뒤섞이는지 확인한다.
- 데스크톱과 모바일 대표 폭에서 가로 넘침, 잘림, 탐색, 폼과 펼침 동작, 키보드 조작, 입력 레이블과 포커스를 확인한다.

**데이터 수집·집계·메타**

- 현재 패치와 시즌을 실제 설정·코드·데이터에서 확인한다. 이 프롬프트 작성 시점의 패치 번호나 시즌을 고정하지 않는다.
- 랭크 스쿼드 필터, 시즌·패치·기간 경계, KST/UTC 변환, 최신 경기 정렬이 일관되는지 검증한다.
- 승률·TOP3·평균 순위·픽률의 분자·분모·집계 단위와 화면의 단위·반올림이 맞는지 독립 계산으로 확인한다.
- 중복 경기·참가자, 페이지·커서 경계의 누락, 실험체·무기 조합 유효성, 완성 스쿼드 기준 2인/3인 조합 중복 제거를 확인한다.
- 랭크 범위 필터가 실제 데이터 범위를 바꾸는지, 현재 패치 데이터가 없을 때 이전 패치 결과를 현재 결과처럼 표시하지 않는지 확인한다.
- 수집 큐·재시도·중복 실행·이어받기·부분 실패·요청 제한·시간 초과를 로컬 테스트나 모의 응답으로 검증한다.

**플레이어 분석과 추천의 정확성**

- 개인 기록과 비교군의 시즌·패치·MMR·실험체·무기·역할군 범위가 계산과 화면 설명에서 일치하는지 확인한다.
- 미수집·실제 0·분모 0·이상값·표본 부족을 구분한다. 부족한 현재 패치 표본을 이전 패치나 출처 불명 데이터로 채우지 않는다.
- 가능한 원본 표본을 독립 계산해 수치·단위·유효 경기 수와 대조한다. 기대값을 검증 대상 함수의 출력으로 생성하지 않는다.
- 실제 통계와 상대 점수, 전체 개인 경기와 주력 픽 경기, 개인 표본과 비교군 표본을 혼동하지 않는지 확인한다.
- 강점·점검 제안이 실제 관측 방향·신뢰도·비교 기준과 모순되지 않는지 확인한다. 기록 비교는 같은 패치·실험체·무기의 겹치지 않는 두 구간인지 검증한다.
- 추천이 선택 팀원과 개인 사용 이력을 요구사항에 맞게 반영하는지 확인한다. 점수·통계·한국어 설명이 같은 근거를 사용해야 한다.
- AI 키 없음·시간 초과·잘못된 응답에서도 기본 결과가 유지되는지 검증한다. AI가 확정 수치·후보·핵심 근거를 바꾸거나 효과를 보장하지 않아야 한다.
- 관련 코드 변경 후 이전 캐시가 잘못 재사용되지 않는지, 캐시 키와 무효화 범위가 맞는지 확인한다.

**API·운영 안정성**

- 잘못된 JSON, 누락·타입 오류·범위 초과·중복 입력과 상태 코드·사용자 안내를 검증한다.
- 관리자·수집 API의 무인증/잘못된 인증/인증 설정 누락 시 동작을 확인한다. 민감한 작업이 의도하지 않게 공개 실행되는지 조사한다.
- 서버 비밀값의 클라이언트 포함, 오류 응답·로그 노출, 외부 URL import의 허용 범위와 요청 제한을 확인한다.
- 느린 DB/API, 부분 데이터, 빈 결과에서도 성공처럼 잘못된 통계를 제공하지 않는지 확인한다.
- 성능 문제는 조건과 측정값으로 판단한다. 짧은 한 번의 측정으로 일반적인 성능 향상을 단정하지 않는다.

### 3. 문제와 기능 보완의 우선순위

- **P0**: 비밀 노출, 데이터 파괴, 무단 관리 작업, 서비스 전체 장애.
- **P1**: 잘못된 통계·분석·추천, 패치/시즌 혼합, 핵심 사용자 흐름 실패.
- **P2**: 주요 예외 처리 누락, 사용자에게 필요한 기능 공백, 반복되는 사용성·성능 문제.
- **P3**: 낮은 영향의 표시·문구·접근성·유지보수 개선.

재현된 결함과 검증 전 의심 사항을 구분하라. 기능을 추가하려면 해결할 사용자 문제, 기존 기능으로 해결되지 않는 이유, 최소 구현 범위와 수용 기준을 먼저 명시하라. 현재 서비스 목표 안의 명백한 누락은 구현까지 진행한다. 장기 이력 저장·예측 모델·새로운 외부 서비스 등 큰 제품 확장은 별도 제안으로 기록하고 자동으로 범위를 넓히지 않는다.

### 4. 검증 → 구현 → 재검증 반복

각 반복에서 우선순위와 영향 범위를 기준으로 하나의 문제 또는 서로 밀접한 문제 묶음을 선택한다.

1. **재현**: 입력·환경·단계·기대 결과·실제 결과를 기록하고 원인을 좁힌다. 기능 공백은 사용자가 완료하지 못하는 흐름을 제시한다.
2. **수용 기준**: 수정 후 어떤 관측 결과가 나오면 해결인지 먼저 정한다.
3. **구현**: 원인에 필요한 최소 범위로 직접 수정한다. 임의 기본값, 가짜 데이터, 오류 숨김, 무관한 리팩터링으로 해결한 것처럼 만들지 않는다.
4. **회귀 방지**: 계산·필터·인증·비동기 등 중요한 동작 변경에는 문제를 재현하는 회귀 테스트를 추가한다. 가능하면 수정 전 실패와 수정 후 통과를 확인한다. 단순 문구·여백 수정에는 불필요한 테스트를 만들지 않는다.
5. **재검증**: 관련 테스트와 실제 흐름을 다시 확인하고 인접 기능의 회귀를 점검한다. UI 수정은 가능한 브라우저로 실제 화면과 상호작용을 확인한다.
6. **기록·다음 선택**: 근거와 결과를 문서에 갱신하고 다음 우선순위 항목으로 진행한다. 항목 하나를 고치거나 테스트 하나가 통과했다는 이유로 전체 작업을 종료하지 않는다.

테스트 실패를 없애려고 기대값을 무조건 바꾸거나 테스트를 삭제·건너뛰지 않는다. 요구사항 자체가 잘못된 경우에는 독립 근거를 기록하고 구현과 테스트를 함께 정정한다. 접근할 수 없는 API·브라우저·DB 검증은 통과로 간주하지 않으며, 가능한 로컬 검증을 계속한다.

### 5. 검증 명령과 증거

저장소의 현재 스크립트를 확인한 뒤 다음 명령을 기본으로 사용한다.

```powershell
pnpm typecheck
pnpm test
pnpm build
```

개별 수정 중에는 관련 테스트부터 실행한다. 최종 변경 상태에서는 타입 검사·전체 테스트·프로덕션 빌드를 확인한다. 같은 최종 상태에서 이미 통과한 검사를 이유 없이 반복하지 않는다. 기존 서버가 같은 빌드 산출물을 사용 중이면 간섭을 피할 실행 방법을 먼저 확인한다.

플레이어 분석을 변경하면 기존 검증 문서와 도구를 확인하여 고정 표본 감사도 활용한다.

```powershell
node scripts/audit-player-analysis.mjs --input tests/fixtures/player-analysis-real-cases.json --cohorts none --out .scheduler/player-analysis-offline-audit.json
```

이 감사는 고정 표본에 대한 오프라인 검증이다. 실제 DB 비교군·최신 API·브라우저 검증의 통과를 의미하지 않는다. 기존 검증 문서의 당시 결과도 이번 실행의 결과와 구분한다.

실제 외부 연동은 읽기 전용 확인부터 진행한다. 조회처럼 보이는 분석·추천 요청도 수집·캐시 저장을 수행할 수 있으므로 구현을 먼저 확인한다. 데이터 변경이 필요한 검증은 로컬·격리 환경에서 진행한다. 실제 API가 최신 필드나 게임 규칙과 맞는지 불확실하면 공식 문서를 확인한다.

### 6. 진행 기록과 재개

다음 파일을 만들거나 기존 내용을 갱신한다. 날짜와 실행 환경을 함께 기록한다.

- `docs/qa-backlog.md`: ID, 영역, 상태, 우선순위, 사용자 영향, 재현 또는 검증 단계, 기대/실제 결과, 수용 기준, 증거, 후속 작업.
- `docs/qa-progress.md`: 실행별 검증 범위, 수정 항목, 테스트 명령·결과, 브라우저 확인 결과, 미검증 범위, 차단 원인, 다음 시작 항목.

미검증·외부 조건 차단 항목은 결함으로 확정하지 않는다. 해결 항목은 삭제하지 말고 검증 근거와 함께 상태를 갱신한다. 증거는 재현에 필요한 최소 내용만 저장하며 비밀값과 불필요한 개인 식별자는 제거한다.

처음 실행할 때는 핵심 기능 전체를 한 번 점검하고, 이후 실행에서는 변경 영역·미해결 우선순위 항목·핵심 회귀 흐름을 중심으로 진행한다. 남은 작업을 문서에만 옮기고 바로 종료하지 말고, 현재 환경에서 구현·검증 가능한 항목을 계속 처리한다.

### 7. 실행 범위와 종료 기준

일반적인 코드·테스트·문서 수정은 이 요청의 범위 안에서 진행하고, 구현 선택을 반복해서 사용자에게 되묻지 않는다. 기존 데이터 삭제·대량 운영 데이터 수정·운영 마이그레이션·예약 작업 변경·배포·push는 이번 QA 요청만으로 실행하지 않는다. 필요한 경우 로컬에서 검토 가능한 변경과 검증 근거를 먼저 준비한다.

이번 실행은 핵심 흐름 점검이 끝나고, 발견된 P0/P1 및 이번 실행에 선정한 보완 항목이 수정·재검증되었을 때 마무리한다. 외부 조건 때문에 완료할 수 없는 항목은 차단 원인과 필요한 조치를 분명하게 남긴다. 범위 내 개선이 완료되었다면 억지로 문제나 기능을 만들지 않는다. 실행을 중단해야 하면 완료한 범위와 남은 범위를 나누어 다음 실행이 즉시 이어질 수 있도록 기록한다.

작업 중에는 무엇을 확인했고 다음 검증으로 무엇을 해결할지 간결하게 공유한다. 마지막에는 다음 내용을 한국어로 보고한다.

1. 수정한 문제·기능과 사용자에게 달라진 점.
2. 실제 실행한 검증과 결과, 새 변경으로 생긴 실패와 기존 실패의 구분.
3. 남은 결함·미검증·외부 차단 항목과 영향.
4. 다음 실행의 우선순위와 진행 기록 경로.

확인하지 않은 내용을 정상으로 단정하거나 프로젝트 전체에 결함이 없다고 선언하지 마라. 이제 현재 저장소에서 첫 검증과 개선 작업을 시작하라.
